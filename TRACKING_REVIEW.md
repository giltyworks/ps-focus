# Core tracking review - 12 October 2026

## Fixed in 1.1.20

- **Subsecond loss and incorrect day/hour attribution.** Persist actual elapsed duration rather than rounding each program up to whole seconds later. Split every interval at local hour/day boundaries. Commit fractional time at each normal tick and focus transition, and flush before shutdown UI/settings/backup work. Existing history schema already stores REAL seconds; no destructive migration.
- **Failed write loss and state confusion.** Pending day/hour/program buckets stay in memory until the entire SQLite transaction succeeds. Current foreground state advances even when a write fails, so retries do not credit the previous app twice or credit it for the new app's interval. All buckets and first-session times commit atomically.
- **Exit during a temporary database failure.** Save unsaved buckets to an atomic local `activity.pending.json` recovery file. Next startup replays it with a receipt stored in the same database transaction. If a crash occurs after replay but before removing the file, the receipt prevents duplication. Invalid recovery files are preserved, and an existing recovery file is not silently overwritten.
- **Sleep/hibernate credit.** Measure elapsed awake time with Windows QueryUnbiasedInterruptTime, rather than a clock that includes suspend time. Wall-clock changes do not change elapsed credit. [Microsoft API documentation](https://learn.microsoft.com/en-us/windows/win32/api/realtimeapiset/nf-realtimeapiset-queryunbiasedinterrupttime).
- **Lock screen/secure desktop.** Check whether the thread's desktop is receiving input before accepting the foreground program, excluding stale handles behind a lock screen or secure desktop. [Microsoft desktop information documentation](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getuserobjectinformationa).
- **Idle API failures.** A failed Windows last-input query no longer assumes that the user is active. The existing 32-bit tick-wrap calculation is covered by tests.
- **Durability.** SQLite remains in WAL mode but now uses synchronous=FULL, flushing each committed transaction instead of accepting the acknowledged-write loss possible with NORMAL after an OS crash/power loss. This adds a disk sync and still depends on correctly functioning storage. [SQLite durability documentation](https://www.sqlite.org/pragma.html#pragma_synchronous).
- **Visible failure.** Failed save/refresh displays TRACKING ERROR in red with a tooltip; recovery clears it. SQLite lock waits are limited to 100ms rather than blocking the GUI for the default five seconds.

## Verified scenarios

Regression tests cover hour/midnight boundaries, first-session timestamps, fractions across app switches, reopening the database, 150 seeded short foreground/idle/pause transitions compared against an independent ledger, failed/locked transactions and retry, interrupted recovery cleanup without duplication, invalid recovery data, fractional shutdown during a write failure, paused/idle intervals, Windows desktop checks, executable-based detection for all supported programs, missing/inaccessible process handles, input tick wrap, and the failed-input-query path. Existing tests cover tray/minimized tracking, pause controls, backup/restore, and per-program history. All 268 tests and the final source/package credential audits and Windows/offscreen packaged startup checks passed. Installed and reopened 1.1.20 successfully; checksum and handover are recorded in HANDOVER.md.

Local microbenchmark (100 samples, temporary database): FULL commit median 0.979ms, p95 1.221ms, maximum 1.458ms. Foreground check median 0.028ms, p95 0.052ms, maximum 0.383ms. This is a local snapshot, not a guarantee on slower disks. No actual Windows lock/sleep cycle or interactive Photoshop session was performed during this audit; native API behaviour was checked against official documentation and mocked regression tests, with actual awake-clock calls and packaged startup smoke checks.

## Remaining accuracy limits

- Foreground changes are sampled every 100ms while the UI event loop is responsive. Events inside that gap cannot be timestamped exactly; rapid switches that occur entirely between samples may be missed.
- **Important:** sampling and SQLite recording still run on the UI thread. Slow backup/restore operations or another UI stall can delay sampling. The existing two-second maximum credit per unobserved interval intentionally avoids guessing that the old app stayed foreground, so a longer stall may undercount real activity. Resolving this requires an independent sampling/recording worker or a timestamped foreground-event stream; simply removing the cap would risk counting time in the wrong app. This remains a meaningful follow-up, especially given the user's accuracy requirement.
- A forced kill/crash before the next transaction can lose the current uncommitted interval. Orderly exit flushes it; the failure journal protects orderly shutdown with a temporary SQLite failure. If both the database and recovery file are unwritable, or the disk is full/damaged, software cannot guarantee persistence.
- Wall-clock or timezone changes can reposition a small interval's day/hour bucket; elapsed duration uses the independent awake clock and remains bounded. Repeated DST hours intentionally share the existing hour bucket.
- Tracking means a supported program is foreground and Windows has seen user input within five minutes. It does not prove brush movement; reading a canvas can still be active time. Unsupported/renamed executables are not tracked. Photoshop, Krita, Clip Studio Paint and PhotoCraft are recognised as of 1.1.21; PhotoCraft uses photocraft.exe.

Do not describe this as proven flawless. The fixed cases now have regressions; the independent-worker issue and short sampling window are explicit remaining limits.
